Yes. What you are describing is no longer a conventional chatbot. It should be designed as an **in-app AI Agent / Copilot that understands the entire application, can answer from live application data, navigate the application, perform permitted actions, and request human approval before mutations**.

The most important change is this:

> If a user asks “How many supervisors do we have?”, the assistant should understand that the user almost certainly wants the **useful operational answer**, not merely the number.

So instead of:

> “We have 6 supervisors.”

it should proactively return something like:

| # | Supervisor  | Assigned Site   | Company   | Status |
| - | ----------- | --------------- | --------- | ------ |
| 1 | Ahmed Ali   | Arabian Ranches | Company A | Active |
| 2 | John Mathew | Damac Lagoon    | Company A | Active |
| 3 | ...         | ...             | ...       | ...    |

Then:

> **Total: 6 supervisors.**
> I found 6 active supervisors across 6 assigned sites.

This needs to be a **product-level behavior and architecture rule**, not just a prompt.

Below is the PRD I recommend implementing.

# PRODUCT REQUIREMENTS DOCUMENT

# AI AGENT / INTELLIGENT APP ASSISTANT

### Full In-App Knowledge, Live Data, Navigation, Action Execution & Human Verification

**Product:** Existing Business Management Application

**Version:** 1.0

# 1. EXECUTIVE SUMMARY

The existing AI Assistant must evolve from a basic question-answering chatbot into an **application-aware AI Agent** capable of:

* Understanding the entire application.
* Understanding every sidebar menu.
* Understanding every submenu.
* Understanding every page.
* Understanding buttons and their purposes.
* Understanding forms and fields.
* Understanding tables and filters.
* Understanding user permissions.
* Reading live application data.
* Presenting complete answers instead of minimal answers.
* Automatically expanding useful supporting information.
* Navigating the user through the application.
* Performing actions inside the application.
* Creating and editing records.
* Reading pasted operational messages.
* Converting unstructured messages into structured actions.
* Asking only for information genuinely missing.
* Preparing actions before execution.
* Requiring human verification before data-changing operations.
* Confirming completed actions.
* Remaining strictly inside the application.
* Never navigating users to external websites or services.
* Maintaining an audit trail of every agent action.
* Handling large datasets through pagination/querying rather than dumping huge datasets into chat.

The assistant should behave more like:

> **“An intelligent employee who understands how this application works and can operate it under human supervision.”**

rather than:

> **“A chatbot that answers questions.”**

If the user asks:

> “How many supervisors do we have?”

You currently have 6 supervisors.

|---|------------|---------------|---------|--------|

The assistant must **never invent fields or values**.

# 5. ANSWER EXPANSION RULE

The assistant should automatically include supporting information when:

1. The information directly explains the answer.
2. It is available from the application.
3. It is reasonably useful.
4. It does not expose unauthorized information.
5. It does not create an unnecessarily huge response.

The assistant should NOT ask:

> “Do you also want the names?”

when names are obviously useful and available.

Instead, provide the names.

# 150. THE MOST IMPORTANT RULES

The engineering team should treat these as non-negotiable:

### 1. Don't build a chatbot. Build an application agent.

### 2. Don't make the user ask twice.

When the answer naturally includes names, assignments, status or other useful information, provide them proactively.

### 3. Don't give the LLM unrestricted access.

Use registered, permission-controlled application tools.

### 4. Don't let the AI guess critical information.

Ambiguous employee, company, document or NOC information must be resolved by the user.

### 5. Every important edit requires human verification.

The AI proposes; the human approves; the application executes.

### 6. The AI must verify its own work.

Never say "Done" without confirming the operation succeeded.

### 7. The AI must understand the UI.

Maintain a structured UI registry containing menus, pages, buttons, actions and permissions.

### 8. The AI must remain inside the application.

No external navigation or external actions.

### 9. Use the application's existing services.

NOC generation, document management, stamping, ZIP generation and other workflows must have one source of truth.

### 10. The chat is an application interface, not a text box.

Tables, cards, pagination, document previews, action buttons, progress states and confirmation panels must be first-class UI components.

### 11. The assistant must understand context.

If the user is viewing an NOC and says "stamp this", the agent should know which NOC "this" refers to.

### 12. The assistant should behave like a capable employee under supervision.

It should investigate, prepare, execute approved work, verify the outcome, and clearly report what happened.

This architecture also fits the NOC/document work we already defined: the agent should call the **existing NOC, stamping, employee-document and ZIP services**, rather than implementing parallel AI-specific versions. That keeps the normal UI and AI Agent behavior consistent and prevents exactly the sort of wrong-stamp, stale-record, incomplete-NOC, and document-selection bugs you've been fixing.
