# PRODUCT REQUIREMENTS DOCUMENT

## Documents, NOC ZIP Package & Stamp System — Enhancement and Fix Specification

**Module:** Documents / NOC
**Feature Area:** NOC Document Packaging, Employee Documents, Stamp Management
**Status:** Implementation Specification
**Priority:** High / Production
**Scope:** Existing Web Application — Documents Module

---

# 1. OBJECTIVE

Enhance the existing Documents and NOC module so that, after an NOC is finalized, the user can generate a complete document package containing:

1. The finalized NOC.
2. One employee ZIP file for every employee included in that NOC.
3. Each employee ZIP containing the latest valid:

   * Passport Copy
   * Emirates ID / ID Card Copy
   * Visa Copy
   * Medical / Other document where applicable
4. Missing documents must not prevent ZIP generation.
5. Only available and valid documents should be included.
6. The final package must itself be compressed into a single ZIP named after the NOC.
7. Both PDF and image documents must be supported.
8. Documents must have preview functionality.
9. Employee documents must be displayed in a clean two-column layout.
10. Stamp selection must use the correct database stamp.
11. Stamp names and actual stamp files must never become mismatched.
12. The stamp animation must visually show the stamp falling onto the correct location on the NOC.

The feature must integrate into the existing Documents/NOC module.

# 10. LATEST VALID DOCUMENT RULE

This is a critical backend requirement.

When generating the NOC ZIP package, the system must **not simply use the first document returned by the database**.

For every employee and every required document category:

```text
Find all records
    ↓
Remove invalid records
    ↓
Remove deleted records
    ↓
Remove unusable files
    ↓
Sort by latest valid record
    ↓
Use newest valid file
```

The selection rule should be:

```text
latest valid uploaded document
```

preferably based on:

```text
uploaded_at DESC
```

with a deterministic secondary ordering such as:

```text
id DESC
```

# 12. VALID DOCUMENT DEFINITION

A document is considered valid for packaging when:

* Database record exists.
* File exists in storage.
* File is readable.
* File has an accepted MIME type.
* File is not marked deleted.
* File is not corrupted.
* File belongs to the employee.
* Document category matches the requested category.

If a document record exists but the physical file is missing:

```text
Invalid
```

and it must not be packaged.

# 13. STORAGE CLEANUP

The employee document repository must not accumulate unnecessary duplicate files indefinitely.

The system should identify obsolete/unusable document records.

Examples:

```text
old passport
duplicate upload
broken file
orphan database record
deleted document
unsupported document
```

These should be removed according to the document retention policy.

However, **do not automatically delete a document merely because it is old if that document is referenced by a finalized NOC or required for audit/history**.

Historical NOC references must remain safe.

Recommended model:

```text
Employee current documents
        ↓
Latest valid document
```

while:

```text
Finalized NOC
        ↓
Historical document reference/snapshot
```

remains immutable.

# 24. PACKAGE SHOULD NOT MODIFY EMPLOYEE RECORDS

ZIP generation is a read/package operation.

It must not:

* Change employee information.
* Change passport information.
* Change document ownership.
* Replace employee documents.
* Modify NOC employee snapshots.

It simply retrieves the correct current valid files and packages them.

### Current problem

The UI displays one stamp name but another stamp is actually applied.

```text

```

```text

```

---

# 29. STAMP MUST USE DATABASE ID

Never select a stamp based only on:

```text
stamp_name
```

Do not do:

```text
WHERE name = "Dubai Stamp"
```

as the actual stamping identity.

Use:

```text
stamp_id
```

Example:

```text
{
    "stampId": "stp_004"
}
```

Then backend loads:

```text
noc_stamps.id = stp_004
```

and retrieves the exact associated image.

# 36. STAMP TARGET POSITION

The stamp must have a defined target position in the NOC template.

Do not simply place it at:

```text
x = 50%
y = 50%
```

The template should define:

```text
stamp_position
stamp_width
stamp_height
stamp_rotation
```

Example:

```text
{
    "x": 450,
    "y": 690,
    "width": 120,
    "height": 120,
    "rotation": -8
}
```

The actual coordinates must be calibrated against the approved A4 NOC template.

---

# 37. ANIMATION AND PDF MUST USE THE SAME POSITION

The biggest requirement for visual correctness:

```text
Animation position
        =
Final PDF stamp position
```

The frontend animation should use the same normalized coordinates as the backend renderer.

Otherwise the animation may show the stamp hitting one location while the final PDF places it somewhere else.

---

# 38. RECOMMENDED POSITION MODEL

Use normalized coordinates:

```text
x: 0.72
y: 0.82
width: 0.18
height: 0.12
rotation: -8
```

Then:

```text
Frontend
+
Backend PDF renderer
```

both calculate the physical position from the same values.

This avoids screen-size-dependent errors.

# 40. STAMP IMPACT EFFECT

At the moment the stamp lands:

* Very small scale compression.
* Slight rotation correction.
* Tiny bounce.
* Subtle shadow.
* Optional subtle paper-impact effect.
* Stamp opacity transitions from preview/translucent to final.
* Final stamp remains exactly where it landed.

Avoid excessive effects. It should feel premium and professional rather than like a game.

# 49. ZIP SECURITY

ZIP packages contain highly sensitive employee documents.

Therefore:

* ZIP generation requires authentication.
* User must have NOC/document access permission.
* Generated ZIP must be stored privately.
* Download should use authenticated access or a short-lived signed URL.
* ZIP URLs must not be publicly guessable.
* Audit the package generation/download.
* Do not expose employee documents through public storage.

# 55. ZIP ERROR HANDLING

If one employee's document cannot be read:

```text
Employee ZIP creation failed
```

should not necessarily destroy the entire package.

The system should continue processing the remaining employees.

At completion:

```text
20 employees
19 packages successful
1 package failed
```

Then display the affected employee.

However, if the NOC PDF itself cannot be generated/read, the overall package should fail because the NOC is mandatory.

# 61. ACCEPTANCE CRITERIA — LATEST DOCUMENT

Given:

```text
Passport A — January
Passport B — February
Passport C — March
```

the ZIP contains:

```text
Passport C
```

If Passport C is invalid/missing:

```text
Passport B
```

is selected.

If no valid passport exists:

```text
No Passport file
```

is added, and ZIP generation continues.

       ↓

# 68. FINAL PRODUCT PRINCIPLE

The Documents module should now operate as a complete document-management and NOC-production system:

```text
EMPLOYEE DATABASE
       │
       ├── Employee Information
       │
       └── Employee Documents
              │
              ├── Passport
              ├── Emirates ID
              ├── Visa
              └── Medical / Other
                         │
                         ↓
                    NOC CREATION
                         │
                         ├── Company
                         ├── Client
                         ├── Project
                         └── Employees
                         │
                         ↓
                    FINAL NOC
                         │
             ┌───────────┼───────────┐
             │           │           │
           Print      Download     Stamp
                                     │
                                Select Stamp
                                     │
                              Animated Apply
                                     │
                              Stamped NOC
                                     │
                                     ↓
                              ZIP DOCUMENTS
                                     │
                     ┌───────────────┴──────────────┐
                     │                              │
                  NOC PDF                     Employee ZIPs
                                                    │
                                      ┌─────────────┼─────────────┐
                                      │             │             │
                                  Passport      Emirates ID     Visa
                                      │             │             │
                                      └─────────────┴─────────────┘
                                                    │
                                                    ↓
                                           FINAL NOC PACKAGE
                                                    │
                                                    ↓
                                         Download to Device
```

The core architectural rule remains:

**Employee database = source of truth.**

**Employee document repository = latest valid document source.**

**NOC = historical snapshot.**

**Stamp = independent NOC-level action.**

**ZIP = generated delivery package, not the source of truth.**

This structure will allow the system to scale to a very large number of employees, NOCs and documents without loading the entire document repository into the browser or mixing historical NOC data with current employee records.
